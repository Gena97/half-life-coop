# Установка и обновление Half-Life Co-op

Для установки и запуска мода достаточно одного `HLCoopLauncher.exe`. Положите его куда удобно, например на рабочий стол, и откройте. Подготовленная версия 0.4.10 использует нативный установщик и обновлятор на C++, без PowerShell во время работы EXE

Нужны Windows и установленная оригинальная Half-Life из Steam. Half-Life: Source не подходит. Запускатель находит игру в библиотеках Steam, устанавливает встроенный пакет в `Half-Life/hlcoop` и запускает мод. Если найти игру не удалось, появится выбор папки с `hl.exe` и `valve`. Выбранная папка запоминается

Для следующих запусков открывайте этот же EXE, поэтому после установки его нужно оставить. Он обновляется на своём месте. Ярлыки не создаются, отдельная копия EXE в AppData не устанавливается. В `%LOCALAPPDATA%\HalfLifeCoop` хранятся выбранная папка игры и журналы

## Что происходит при следующих запусках

Запускатель проверяет последний стабильный GitHub Release. Сначала загружаются `launcher-update.json` и его отделённая подпись `launcher-update.sig`. Подпись RSA 3072 / SHA256 проверяется открытым ключом, встроенным в EXE. Затем проверяются адрес репозитория, тег, версия, имя файла, размер и SHA256 нового EXE. Неподписанное или изменённое обновление не устанавливается

Отдельный экземпляр этого же EXE ждёт закрытия текущего процесса, повторно проверяет файлы, заменяет запускатель и открывает новую версию. При ошибке выполняется откат. Для обновления рядом с EXE создаётся временная папка на том же диске; успешная операция убирает её

В новый EXE уже встроены файлы мода в CAB MSZIP и манифест их размеров и SHA256. После обновления запускатель устанавливает эту версию мода, сохраняя пользовательские данные. Во время работы игры файлы не заменяются. При недоступном GitHub используется доступная локальная версия

Обычный `hlcoop/start-hlcoop.cmd` тоже поддерживается: он проверяет и обновляет файлы мода. Проверка нового EXE выполняется при запуске `HLCoopLauncher.exe`. Сам запуск Half-Life и приглашение Steam проверку обновлений не вызывают

## Параметры EXE

Папку игры можно передать явно, например для второй установленной копии:

```powershell
.\HLCoopLauncher.exe --game-dir "F:\Games\Half-Life"
```

`--install-only` устанавливает или обновляет мод, затем завершает работу без запуска игры

`--skip-update` отключает сетевые проверки EXE и мода. Установка из встроенного пакета при этом работает. Для установки без сети и без запуска игры:

```powershell
.\HLCoopLauncher.exe --game-dir "F:\Games\Half-Life" --install-only --skip-update
```

## Старый запуск через CMD

Git и вход в GitHub игрокам не нужны. EXE обращается к публичному репозиторию `Gena97/half-life-coop`, адрес задан при сборке. Описанный ниже `update.json` управляет только старым запуском через `start-hlcoop.cmd`

Параметры мода находятся в `Half-Life/hlcoop/update.json`:

```json
{
  "schemaVersion": 1,
  "repository": "Gena97/half-life-coop",
  "enabled": true,
  "mode": "automatic",
  "assetPrefix": "hlcoop",
  "timeoutSeconds": 15
}
```

`enabled: false` отключает проверку мода, `mode: "notify"` сообщает о новой версии без её установки, `mode: "automatic"` устанавливает обновление перед запуском. Пустой `repository` отключает сетевую проверку мода. Эти настройки не управляют обновлением самого EXE; для пропуска обеих проверок есть `--skip-update`

Для собственного репозитория адрес в исходном `game/hlcoop/update.json` меняют перед сборкой: из него создаётся настройка EXE. Установленный `update.json` не меняет адрес нативного обновлятора. Уже существующий файл у игрока сохраняется

## Сохранение данных

Нативный установщик проверяет встроенный манифест, размеры и хеши файлов, номер версии и допустимые пути. Существующие `*.cfg`, `settings.scr`, `CSBotConfig.vdf`, сохранения и журналы не заменяются. В CAB нет CMD, PowerShell-скриптов или настроек старого обновлятора. Оригинальные файлы Half-Life не входят в пакет

Перед заменой файлов мода создаётся резервная копия. При ошибке выполняется откат. Если откат не завершён или предыдущая установка была прервана, запуск блокируется; путь к резервной копии записан в `hlcoop/.hlcoop-update-transaction.json`

В установках с прежним обновлятором можно проверить наличие обновления мода без запуска игры:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\путь\Half-Life\hlcoop\update-hlcoop.ps1" -CheckOnly
```

## Выпуск через GitHub Actions

Перед первым выпуском нужно настроить ключ подписи, как описано ниже. Workflow запускается при отправке тега вида `v0.4.10`. Номер должен совпадать с `version` в `game/hlcoop/liblist.gam`. После сохранения изменений в Git:

```powershell
git push origin main
git tag v0.4.10
git push origin v0.4.10
```

Workflow проверяет ключ подписи, собирает библиотеки мода и совместимый ZIP, затем создаёт CAB и нативный запускатель. После необязательной подписи Authenticode создаётся подпись манифеста обновления. Готовые файлы проверяются и сканируются включённым Defender с актуальными базами. Ошибка или обнаружение останавливают публикацию

В черновик Release загружаются семь файлов, затем он публикуется целиком:

- `hlcoop-0.4.10-win32.zip`
- `hlcoop-0.4.10-win32.zip.sha256`
- `HLCoopLauncher.exe`
- `HLCoopLauncher.exe.sha256`
- `launcher-update.json`
- `launcher-update.sig`
- `release-verification.json`

ZIP нужен для ручной установки и обновляторов прошлых версий. EXE публикуется отдельно и в ZIP мода не входит

Actions закреплены по конкретным коммитам официальных репозиториев. Переменная репозитория `HLC_ENABLE_ATTESTATIONS=true` дополнительно включает аттестацию происхождения EXE средствами GitHub

Если тег уже отправлен, откройте **Actions → Release mod → Run workflow**, выберите `main` и укажите существующий тег в поле `release_tag`. Ручной запуск берёт исходники из выбранного тега. Удалять или переносить тег для повторной попытки не нужно

Изменение файлов в ветке без нового релиза не обновляет установленные копии. Для исправленной сборки выпускайте новый номер: одинаковая версия повторно не устанавливается. Черновики, предварительные релизы и версии ниже установленной пропускаются

## Сборка и публикация вручную

Нужны Visual Studio 2022 с инструментами C++ для x86/x64, Windows SDK и закрытый ключ обновлений. Выполняйте команды по порядку: CAB для EXE создаётся из уже готового ZIP текущей версии

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\build.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\package.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\build-launcher.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\sign-authenticode.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\sign-launcher-update.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify-launcher-release.ps1 -UpdateSignatures
```

Готовые файлы находятся в `artifacts`. При необходимости передайте `build-launcher.ps1` параметры `-PackagePath` и `-OutputDirectory`

Без настроенного сертификата `sign-authenticode.ps1` оставляет EXE неподписанным и сообщает об этом. Подпись манифеста обновления обязательна. После любой замены или переподписи EXE повторите `sign-launcher-update.ps1` и проверку релиза

`verify-launcher-release.ps1` записывает хеши шести файлов релиза, результат проверки подписи, ресурсов EXE и сканирования Defender в `release-verification.json`. Проверка использует режим custom scan с `-DisableRemediation`: он проверяет и исключённые пути, и архивы, а при обнаружении останавливает выпуск без лечения файла. Сам Defender и защита в реальном времени остаются включены. Выключенная защита, устаревшие базы и ошибки сканирования также блокируют выпуск. Скрипт не меняет настройки защиты и не добавляет исключения

Создайте GitHub Release с тегом `v0.4.10`, загрузите семь файлов из списка выше в черновик, затем опубликуйте релиз целиком. Используйте пакет без `-IncludeSymbols`. Автоматический архив GitHub `Source code (zip)` для установки мода не подходит

## Ключ подписи обновлений

Открытый ключ хранится в `launcher/update-public-key.json` и встраивается в EXE. Закрытый ключ в Git не попадает. Для этого проекта он хранится в `%LOCALAPPDATA%\HalfLifeCoopDeveloper\update-signing-key.xml`, с доступом только текущему пользователю и SYSTEM

`scripts/init-update-signing.ps1` создаёт новую пару RSA 3072 только при первоначальной настройке. Существующие ключи не заменяются. Закрытый ключ нужно сохранить отдельно: потеряв его, выпустить обновление, которому доверяют установленные EXE, не получится

Для GitHub Actions добавьте секрет `HLC_UPDATE_PRIVATE_KEY_BASE64`. Для следующей команды нужен GitHub CLI и вход через `gh auth login`. Команда передаёт ключ в GitHub по стандартному вводу и не выводит его в консоль:

```powershell
$keyPath = Join-Path $env:LOCALAPPDATA 'HalfLifeCoopDeveloper\update-signing-key.xml'
$keyBytes = [System.IO.File]::ReadAllBytes($keyPath)
try {
    [Convert]::ToBase64String($keyBytes) | gh secret set HLC_UPDATE_PRIVATE_KEY_BASE64 --repo Gena97/half-life-coop
    if ($LASTEXITCODE -ne 0) { throw 'Не удалось сохранить секрет GitHub' }
} finally {
    [Array]::Clear($keyBytes, 0, $keyBytes.Length)
}
```

Перед сборкой workflow проверяет, что закрытый ключ соответствует открытому. Без секрета или при несовпадении публикация останавливается

## Подпись издателя Windows

Сертификата Authenticode у проекта сейчас нет, поэтому EXE не имеет подтверждённого Windows издателя. Подпись RSA манифеста проверяет источник и целостность обновлений, но не заменяет сертификат Authenticode и репутацию SmartScreen

Если сертификат появится, для workflow можно задать секреты `HLC_AUTHENTICODE_PFX_BASE64`, `HLC_AUTHENTICODE_PFX_PASSWORD` и, при необходимости, `HLC_AUTHENTICODE_THUMBPRINT`. Подпись ставится до создания манифеста обновления, затем проверяется средствами Windows. Самоподписанный сертификат доверенным издателем не считается

## Что проверено

17 октября 2026 года сборка 0.4.10 проверена на отдельных папках, в том числе с пробелами и кириллицей в пути. Первая установка завершилась, все 21 файл совпали с манифестом. В установленном пакете нет PS1, CMD и BAT

Проверены переход с ZIP версии 0.4.9, совместимость прежнего манифеста, восстановление повреждённого файла, отсутствующего конфига и liblist.gam. Прерванная установка восстановлена по журналу и резервной копии. Изменённые конфиги и сохранение сохранились. Рабочие установки игры не менялись, игра не запускалась

Нативный обновлятор получил сведения о последнем релизе с настоящего GitHub API. Проверка подписи средствами Windows CNG приняла правильную RSA-подпись и отклонила повреждённую. Обновление на ту же версию отклонено без замены EXE

Готовые EXE и ZIP прошли локальное сканирование Microsoft Defender. Это результат проверки конкретных файлов с текущими базами, а не гарантия отсутствия будущих обнаружений. Отчёты проверок находятся в artifacts. Версия 0.4.10 пока не опубликована

Самообновление EXE через настоящий GitHub Release пока не проверено от начала до конца: для этого нужен опубликованный релиз запускателя со следующим номером версии
